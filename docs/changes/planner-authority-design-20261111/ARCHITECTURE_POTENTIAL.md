# 现有预瞄规划架构的潜力、成本与升级判断

2026-11-11，北京时间。状态：源码核查与工程建议，尚非用户确认的新实施范围。基线为 `METRIC_EXPERIMENT_20261111_4`；已确认的目标设计见 [ADR-0001](../../adr/0001-planner-near-authority.md)。不将目标设计视为当前 r4 已实现，也不将当前主仓库其他增量混入 r4。

## 总体判断

这条分层路线有继续投入的价值。当前算法核心较小、计算有界、复用原双轮 PI 与唯一输出，可以逐步加入经验模型、响应补偿乃至局部 MPC。当前主要问题是旧控制与新监督交叉、输入准入较脆弱、拒绝与最终零输出原因难以定位。继续叠加预测器之前应先消除这些交叉。

“框架提供可能性，算法和参数实现潜力”基本成立，但需补充：可观测信息、执行器和实时预算共同限定上限；算法也可能改变能力类别。固定路径速度规划升级为联合走线与速度优化，不能仅靠原速度规划器参数实现。黑箱辨识可降低前置精细建模负担，但不能从没有观测到的量中自动恢复真实偏移。

## 当前到底实现了什么

r4 当前是固定路径预瞄速度规划、jerk 参考整形、监督器、旧转向和原双轮 PI。速度核心计算曲率/视距限速与前后向传播；24 次标量二分用于参考整形，不是滚动求解未来多步车辆状态与控制序列的优化 MPC。

证据：[速度核心](../../../.build/metric-experiment-20261111-r4/workspace/tools/speed_planning/speed_planner.c:73)、[转向控制](../../../.build/metric-experiment-20261111-r4/workspace/demo/code/vision_control.c:323)、[项目术语说明](../../MPC_GUIDE.md:7)。它已具有预测与约束思想，其工程名称不能作为已实现标准 MPC 的证据。

## 综合评估

| 维度 | 判断 | 后续收益所在 |
| --- | --- | --- |
| 现阶段性能空间 | 尚有明显可研究空间，但不能量化最高速度或增幅 | 提前识别弯道/可信视野、减少误停、连续恢复、改善 PI 跟踪，比增加求解器更直接。 |
| 长期性能上限 | 分层结构可扩展；当前算法本身不具备联合走线与速度优化能力 | 跟踪延迟、转向响应与侧向能力成为实证瓶颈后，可替换横向或速度模块；逼近抓地极限时才考虑更强的联合预测优化。 |
| 调试难度 | 目前偏高，主要来自交叉决策 | 零输出可能来自输入、对齐、规划准入、候选过期、旧近场、PI 或实验截止；先使每种结果可归因，减少调错参数的机会。 |
| 运行体量 | 核心算法不大，尚无本轮实时资源评估 | 固定容量和固定循环值得保留。文件条目、SDK 源数量或历史证据体积不能直接代表实际链接与执行成本。 |

| 调参/辨识效率 | 黑箱路线适配，但当前链路接通优先 | 先有可重复输入输出，再辨识响应和推荐参数；以不同场次验证，不能用同一观测算法的误差字段自动充当真实地面偏移。 |

## 需要保留与需要收敛的部分

保留固定容量共享核心、原 PI、唯一最终 writer、一致快照和候选身份复核；这些有利于替换内部算法。输出 epoch、配置 revision、采样序号和请求 generation 处理不同身份，不能仅为减少字段而合并。

优先收敛每类决策的所有者：规划器负责道路近场可用性与统一速度约束；转向计算提供有来源的候选；生命周期明确区分启动、普通恢复、零速等待与锁止；最终输出独立执行硬授权和故障约束。目标不是把不同职责全塞入一个巨大状态机，而是同类决定不被多层各做一次。

r4 的 [eligible](../../../.build/metric-experiment-20261111-r4/workspace/demo/code/vision_planner_runtime.c:49)要求旧控制为 RUNNING，[最终 writer](../../../.build/metric-experiment-20261111-r4/workspace/demo/code/vision_actuator.c:195)仍可被旧近场否决，正是已确认需要治理的交叉。独立 `vision_metric_pi.c` 虽在工程中，实际米制动力走 [原 PI 请求](../../../.build/metric-experiment-20261111-r4/workspace/demo/code/vision_speed.c:417)；是否保留诊断入口应明确，不能由文件存在推断运行成本。

## 潜力如何检验

历史 [r4 报告](../metric-control-experiment-20261111/user-report.md:12)中的落地短测没有形成计划，不能据此判断规划性能上限。另一无动力探针的 [三份快照](../metric-control-experiment-20261111/evidence/geometry-probe/snapshots.json)显示固定请求行缺失会影响 near/full；那是另一固件的局部输入证据，不能直接当 r4 同次运行的根因。

建议先保持相同感知、转向、PI、硬件和输出路径，仅比较速度策略。用整次运行完成率、全程平均速度/圈时、误停与恢复、轮速跟踪、动作连续性及耗时衡量收益；不要以峰值目标、仿真平滑或测试 PASS 代替整车收益。实际场地试验需另行组织，本报告没有执行。

每个增量应回答一个问题，并能和简单方案比较：

1. 准入到输出能否重复接通、零输出能否归因；
2. 预瞄速度策略相比简单限速是否提高整次运行表现；
3. 加入黑箱响应模型后，未参与拟合的场次是否仍改善；
4. 只有当分离控制反复受转向/速度/延迟耦合限制时，再验证小规模 MPC 是否值得；
5. 如复杂方案没有可重复收益，保留简单实现，继续改善输入、响应或流程，而不为算法名称增加状态和参数。

## 升级成本与外部一手依据

[ETH 作者 MPCC](https://github.com/alexliniger/MPCC)展示了联合优化路径进度、横向/滞后误差、车辆与赛道约束的路线，也要求位置、方向、纵横速度、横摆等状态及车辆模型。它说明存在更高性能能力类别，不构成本车圈速提升保证。

[Autoware 官方横向 MPC](https://autowarefoundation.github.io/autoware_universe/main/control/autoware_mpc_lateral_controller/)将车辆模型、预测优化、转向延迟与时间常数放入控制设计和调参流程。这支持“更强 MPC 会增加模型与调试维度”的判断，不能把其整车参数照搬给智能车。

MPC 本身也不必天然臃肿。[OSQP 官方代码生成](https://osqp.org/docs/codegen/index.html)可为固定维度 QP 生成不使用动态内存、不依赖外部库的 C 求解器。本车求解耗时、最坏时限及失效处理仍需验证；暂未推荐具体求解器或新增其依赖。
