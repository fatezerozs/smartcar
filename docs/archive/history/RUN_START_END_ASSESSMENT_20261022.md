## 2. 代码证据与现有日志边界

- `demo/code/vision_control.c`：`vc_arm()` 将状态改为 `VC_RUNNING`，记录 `armed_ms`，同时将 duty、steering 设为 0。进入 RUNNING 不等于车轮已经起转。
- `demo/code/vision_actuator.c`：`vd_output_zero()` 清零电机及舵机 PWM，源码明确说明 PWM=0 不保证停车距离。没有等待编码器静止的过程。
- `demo/code/vision_startup.c`：当前 C26 配置通过模式、有效图像、编码器新鲜度和故障门槛调用 `vc_arm_local()`；视觉/断帧故障后可重新捕获并恢复。
- `demo/code/vision_drive.c`：当前 `route_trace_observe()` 在 RUNNING 且观察到图像时启动轨迹，`route_record_stop()` 在软件停车/故障时冻结；`reason=1` 为普通软件停止，`reason=2` 为故障，不能区分 OFF、UART STOP 等全部来源。`route_last_stop.run_ms` 是本次停止时刻减最近一次 `armed_ms`，视觉恢复重启后不代表整次会话时长。
- `demo/code/vision_telemetry.c`：`[LAST_STOP]` 保存最近一次软件停止；`[TRACE_BEGIN]`、`[TRACE_END]` 是停车后导出轨迹的协议边界，不能以串口收到这些行的时间作为实际起止时刻。
- `demo/code/vision_drive.h`：轨迹是 1024 条循环缓存，通常每 60ms 一条，覆盖约 61 秒历史，长时间运行可能覆盖真正的起点，不能靠首条 TRACE 计算完整运行时长。
- `demo/code/app_runtime.c`：运行时约 100ms 一次 `[RUN]` / `[SPEED]`，停车后恢复完整周期报告。周期日志可能错过短暂状态变化；串口接收时间还包含发送和排队延迟。
- `demo/code/vision_speed.c`：`vd_speed_sample_tick()` 在 10ms 安全采样路径读取编码器，提供 `samples`、`sample_ms`、`raw3/raw4` 和 `total3/total4`。`raw` 是按 10ms 归一化的计数，低速/采样间隔变化时会整数截断。`measured_right/left` 在速度控制输出路径更新，停车判定应使用持续采样的数据，不依赖停止后的旧 measured 值。
- `demo/code/track_bayes.c` 与 `app_runtime.c`：有条纹特征和 `ZEBRA` 分类名称，但默认模型未训练，完整赛道模式是观察路径，未形成“斑马线确认→终点→停车”的业务链路。

## 3. 逐飞原生例程能复用什么

功能说明表 `Sheet1!A29:D29` 列出 `E1_02_hall_stopline_detection_demo`（主板霍尔停车检测接口例程）；`A13:D16` 列出编码器、计时器、printf/log 等底层例程；`A32:D33` 列出主板两类编码器采集例程。

实际检查霍尔例程 `逐飞科技/RT1064_Library/Example/Motherboard_Demo/E1_motherboard/E1_02_hall_stopline_detection_demo/user/src/main.c`：

```c
#define HALL_PIN (D4)
gpio_init(HALL_PIN, GPI, GPIO_HIGH, GPI_PULL_DOWN);
if (gpio_get_level(HALL_PIN)) { /* 磁铁触发 */ }
```

这是 GPIO 电平读取示例，没有现成 `is_run_started()` / `is_run_finished()`，也没有替用户控制电机。它要求霍尔模块和磁性标记，不能单凭本项目现有摄像头自动获得同等能力。

接入时有两个必须处理的差异：

1. 例程接线注释写 OUT 接 B10，但实际宏定义是 D4。以原始接线核对、实际板卡和代码配置为准，本次没有核实实物引脚，不直接认定可接任一引脚。项目 `demo/user/src/isr.c` 对 D4 只有清中断标志的模板，没有停车业务。
2. 例程会 `timer_stop/clear/start(GPT_TIM_1)`；本项目 `demo/user/src/main.c` 将同一个计时器作为全局毫秒时钟，启动延时、采样和安全超时都依赖它。只复用 GPIO 读取方式，计时使用连续系统时间戳之差，禁止照搬停表/清表逻辑。

编码器底层已有 `encoder_get_count()` 等原生函数；项目自己的 `board_encoder_read()` 和 `vd_speed_sample_tick()` 已做持续计数与差分，不应再照搬例程的定期清计数方式干扰速度环。

## 4. 推荐方案：运行会话与车轮运动分别记录

第一阶段不增加硬件，先补足日志所需的实际起转/停稳检测。编码器只能确认车轮运动；轮胎空转、抬车、锁轮滑移等情况下不能证明车身位移。若要求车身真实移动，还需对地速度/光流等独立观测。

### 4.1 事件定义

| 事件 | 触发条件 | 用途 |
| --- | --- | --- |
| `RUN_ARM` | 控制器成功获得运行授权 | 建立 run_id，记录授权来源；不是实际起转 |
| `RUN_START` | 授权后新鲜编码器数据确认起转 | 记录起转候选起始时刻和确认时刻 |
| `RUN_STOP_REQUEST` | OFF、UART STOP、故障、切模式或终点请求停止 | 在清零输出前保存原因和反馈；立刻沿用现有停车路径 |
| `RUN_END` | 有效反馈确认两轮静止且输出已撤销 | 记录停稳和持续时间；不能在 PWM 清零时立即发布 |
| `RUN_PAUSE` / `RUN_RESUME` | 视觉中断及重新获得授权 | 保持同一会话，记录中断区间；若曾停稳，另记录运动片段边界 |
| `RUN_ABORT` | 未确认起转就撤销本次运行 | `started=0`，不能编造零时长的正常行驶 |
| `RUN_UNCONFIRMED` | 停车反馈失效或等待确认超时 | 记录停止请求已执行、停稳未知，不发布“已停稳” |

普通 OFF/STOP/故障导致停车都不等于完成赛程；日志另设 `completed=0/1` 与 `end_reason`。只有经验证的终点规则才可设置 `completed=1`。

会话从首次成功授权开始，到显式终止及停稳确认结束；视觉自动重获保持会话 ID，同时每次重新授权增加 segment_id。若中途真实停稳，结束该运动片段而保留会话待恢复，避免既把暂时失线算成一整次跑完，又把真正的停车隐藏掉。重新开跑发生在停稳确认之前时，保留未确认状态和旧事件，不强行合成一次已停稳。

### 4.2 检测规则

- 复用 10ms 编码器采样，检测模块消费每一批新样本；不能把同一份 raw 在主循环里多次计算为连续确认。
- 用采样时原始计数差构造每轮绝对计数窗口，正反计数不能互相抵消；不新增编码器清零。建议在采样点累加整数窗口，避免主循环低频轮询漏掉短暂起转或停稳。
- 起转候选初值：50ms 窗口内任一轮绝对增量至少 3 计数，连续两个窗口确认；两轮都满足时标为双轮确认，只有一轮时标为单轮运动并保留异常信息。这样不把仅单轮运动误判为完全静止。阈值仅为待调试初值。
- 停稳候选初值：100ms 窗口内左右轮绝对增量各不超过 1 计数，连续三个窗口确认；必须同时满足停车请求已生效、两路输出为零。该定义是“低于测量阈值的静止”，需按编码器分辨率、噪声和低速爬行实测校准。
- 数据缺失、样本间隔异常、编码器故障时进入 UNKNOWN，不把没有新计数误当静止。其他类型故障切断动力后，只要编码器采样仍有效，就继续检测滑行至停稳。
- 起转授权前被推动车轮，记录 `EXTERNAL_MOTION`，不计成一次自主起跑。授权后一直未起转，超过可配置等待时间则标记 `start_not_confirmed`；不能仅靠日志检测引入新的自动启动/恢复行为。
- 时间使用 uint32_t 无符号差处理回绕；同时存候选时刻和确认时刻，区分滤波延迟。持续时间从明确选定的起转边界到停稳边界计算，另存授权时长，不能混用。

### 4.3 接入位置与传输

1. 新增纯整数检测模块，例如 `run_monitor.c/.h`，保存独立于循环 TRACE 的会话摘要、运动片段及事件队列；不改变控制算法。
2. 在 `vision_speed.c::vd_speed_sample_tick()` 完成计数差计算后喂入样本；该路径停车后仍持续运行。采样中断只做有界整数更新和事件快照，不打印、不等待发送。
3. 在成功授权、`vision_drive_stop()`、故障及安全中断实际切断输出处捕获来源、时间和输出前快照；前台统一收拢事件，防止中断与主循环重复记录。OFF、UART、断帧等应有不同原因枚举；ISR 先切断动力，日志不能延迟停车。
4. 在 `app_runtime.c` 主循环独立轮询事件，在 `vision_telemetry.c` 格式化输出。优先发送小事件，其次周期 RUN，再次大批 TRACE。沿用非阻塞 `app_link_send()`，失败保留待发事件；明确队列容量和溢出计数，并保留最近摘要供查询。
5. 图像模式继续保持二进制帧纯净，文本事件缓存到文字模式再发；记录事件自身的 ms，不拿发出时间代替发生时间。重置前未发数据不保证保留，记录端应把复位视为不完整会话，使用启动标识区分重启后的 run_id。
6. `[STATUS]`/完整报告加入当前 session、segment、motion_state、feedback_valid、最新事件序号和掉事件计数。扩展 `tools/analyze_run_log.py`：按启动标识+run+event_seq 去重，识别缺事件和不完整会话，分别统计授权时间、运动时间、滑行确认时间和暂停区间，不再由循环 TRACE 首尾反推整次时长。
7. 若普通工程编码器未启用，只记录授权与停车请求，并输出 `motion=UNKNOWN source=control_only`；不能输出编码器确认的 START/END。需要物理检测的构建显式启用编码器并验证采样路径。

建议协议示意（字段名与数值均为设计示例，当前代码尚不输出）：

```text
[RUN_EVENT] boot=... run=7 segment=1 seq=1 event=ARM ms=1000 source=C26
[RUN_EVENT] boot=... run=7 segment=1 seq=2 event=START ms=1130 confirmed_ms=1230 source=ENCODER quality=both
[RUN_EVENT] boot=... run=7 segment=1 seq=3 event=STOP_REQUEST ms=8000 reason=SWITCH_OFF
[RUN_EVENT] boot=... run=7 segment=1 seq=4 event=END ms=8350 confirmed_ms=8650 reason=SWITCH_OFF completed=0 feedback=valid
```

## 5. 若“结束”是到达终点

第二阶段单独增加终点来源，不将其与停稳检测混为一谈。

- 有磁条/磁铁和霍尔模块：优先复用原生 GPIO 读取，短周期采样/按脉冲宽度选择边沿捕获，再做有效电平、去抖、离开标记后重装及触发锁存。发车时就在标记上不能立即判完成；按实际赛程定义最短有效时间/距离、允许圈数和终点触发次数。单个磁信号本身无法区分起点、终点或其它磁性干扰。
- 无额外硬件但赛道有明确终点线：另写并验证视觉终点检测，使用多行条纹、时序确认、离开后重装及时间/里程约束；不能把现有未训练 Bayes 的 `ZEBRA` 名称直接当正常结束信号。
- 终点确认先发 `FINISH_DETECTED`，再走现有停车流程。C26 当前可自动恢复，终点必须设置独立完成锁存，直到明确新一轮操作才解除，否则可能刚停又被下一帧有效赛道重新授权。最终 `RUN_END completed=1` 仍需编码器确认停稳。

## 6. 实施后的验证要求

主机测试覆盖：授权但不动、正常起停、停车后滑行、单轮运动、极低速、噪声/抖动、反向、重复样本、丢样本、传感器故障、时间回绕、OFF 与 UART/故障并发、视觉失线恢复、重复停止、起步前被推、超过轨迹缓存时长、发送拥堵和事件溢出。霍尔分支另测：开机在磁条上、持续高电平、多次抖动、未离开重触发、正常完成锁存、OFF→ON 新会话。

上板由操作者核对编码器静止噪声、实际起转门槛和停车滑行，确认阈值及日志先后；主机测试不能证明实车已经停稳。本次是只读代码分析与方案交付，没有运行新的控制测试、编译固件、烧录或实车测试。
