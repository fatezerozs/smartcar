# 速度、稳定性与全程计时验收口径

最新衡量标准为**局部与全程的行驶速度和稳定性**，时间只是其中一项。局部按同一直道、左右弯、十字和圆环分组，记录实际轮速分布、目标跟踪误差、连续通过次数/尝试次数、出界和异常停车；整程记录完整覆盖成功次数/总尝试次数、全部故障及行驶时间。高轮速或扣除停车后的短时间不能抵消出界、漏段或频繁停车。编码器与车轮/传动尚无完整标定，轮速暂用计数/10ms，不冒充m/s。

下面的工具只负责经人工核对的计时和证据，不会自动验证全部速度、稳定性指标。C23的局部与整程验证步骤见[C23现场方案](../archive/versions/C26_23_FIELD_SPEED_AND_PATH.md)。

2026-10-22，操作者确认：从日志附带时间戳及可用视频确定计时边界；跑完全程结束；中途停车不计入行驶时间，但停车必须记录为故障并继续解决。**没有采用“固定 A 起步、回 A 结束”作为已确认规则。**

四项目标保持顺序：不驶出赛道；岔路优先延续当前方向；尽可能覆盖全部赛道；在此前提下缩短全程行驶时间。必须覆盖的实际路段、次数和行驶方向按现场完整赛道及实车记录核对，不能由 C26 开关或环岛状态值代替。尚未取得本轮完整实车记录，因此尚无合格全程成绩，也不能宣布 C22 已实现目标。

## 时间定义

`总经过时间 = 全程完成时刻 - 实际开始行驶时刻`

`停车时间 = 该区间内经核对的停车区间并集长度`

`行驶时间 = 总经过时间 - 停车时间`

总经过时间和停车时间一起保留，不只输出扣除后的数字。若有停车，记录停车次数、时间范围和原因；仍可计算诊断用行驶时间，但不把它排成“已解决故障”的合格成绩。出界、确认漏段或尚未完成全程，不进入合格比较；证据缺失标为待核对，不能假设零停车。

时间标记须在同一个时钟基准内。MCU 32位时钟回绕先展开，复位后的时间不能直接与复位前相减；视频与 MCU 时钟未同步时，不能混用一个的起点和另一个的终点。视频测量误差要覆盖起止帧和全部扣除区间的边界误差，例如30fps下一个帧边界约33ms。成绩区间重叠时不宣称微小差值是确定提升。

## 现有日志能证明什么

- `[RUN]` 是控制器运行状态，不是实际起转或全程完成事件。
- `[SPEED]` 的新鲜 `raw3_L/raw4_R` 可辅助核对车轮运动；单次零计数不能确认停稳，停止后的旧 `measured_R/L` 也不能用于判断。编码器反映车轮，不能证明车身没有打滑或驶出赛道。
- `[LAST_STOP]` / `[SPEED_FAULT]` 用于定位软件停车及原因；请求停车时刻不一定等于实际停稳时刻。
- `[TRACE_END]` 只说明导出结束；完整1024条轨迹也不等于完整赛程，不能拿其首尾时间直接当全程成绩。
- 岛形 `FOLLOW/EXIT` 及十字计数不能独立证明走完圆环或覆盖全部赛道。全程与是否出界须由完整现场观察/视频及相应记录核对。

## 离线验收工具

`tools/evaluate_track_trials.py` 不访问串口，不发送车辆指令，也不修改固件。它检查人工核对后的计时与路段记录，计算停车扣除，校验源文件 SHA256、不同赛道配置、重复/重叠标记与缺失证据。输出明确为 `operator_review`，不会声称自动看懂视频或验证车上固件。

创建本地空模板：

```powershell
python tools/evaluate_track_trials.py recordings/track-trials.json --init
```

模板中的起终点、方向和路段为 `null` / 空对象，必须根据真实记录填写，工具不会替操作者猜测。`include_stops` 按本次要求填写 `false`。`required_passages` 用真实路段名与最低通过次数表达同一条完整路线，不能只列一个容易通过的片段而称为全程；整圈的不同方向或不同覆盖范围须分组。

示意结构（不是实车成绩）：

```json
{
  "course": {
    "id": "现场完整路线的标识",
    "start_rule": "日志与现场记录核对后的实际起跑边界",
    "finish_rule": "同一完整路线全部完成的边界",
    "direction": "填写本组实际行驶方向",
    "conditions": "填写相机、路线、车辆设置及可比条件",
    "include_stops": false,
    "required_passages": {"填写实际必经路段": 1}
  },
  "trials": []
}
```

填完路线后获取指纹：

```powershell
python tools/evaluate_track_trials.py recordings/track-trials.json --fingerprint
```

每条试跑添加以下数据（所有时间是同一基准下的毫秒）：

- `id` 唯一编号；`firmware` 为实际版本；`firmware_sha256` 为实际下载产物的校验值。
- `course_fingerprint` 为上一步指纹；改变方向、规则或必经路段后旧跑次不会自动混入。
- `start_ms`、`finish_ms`、`timing_uncertainty_ms`（大于0，覆盖全部边界误差）。
- `evidence: {"file": "相对本清单的原始记录路径", "sha256": "原始记录的校验值"}`。可指向保存的日志或录像；来源核对责任不能由文件哈希代替。
- `review.reviewer` 为核对人；`continuous_recording`、`on_track`、`route_complete` 为明确的布尔判断，未知时保持 `null`，不能填成已经确认。
- `review.passages` 为 `[{"name": "必经路段名", "from_ms": ..., "to_ms": ...}]`，区间必须处于计时内；同一路段重复/重叠标记不能凑成多圈。
- `review.stops_reviewed` 仅在逐段核对停车后填 `true`；`review.stops` 为 `[{"from_ms": ..., "to_ms": ..., "reason": "视觉丢线/编码器故障/待查等"}]`。核实没有停车才填写空数组。

`Get-FileHash <文件路径> -Algorithm SHA256` 可获取固件或原始记录的 SHA256。

输出报告：

```powershell
python tools/evaluate_track_trials.py recordings/track-trials.json --output recordings/track-report-001.json
```

不会覆盖原始记录、清单或已有报告。输出包括每跑次的经过/停车/行驶时间、故障停车次数、原因、证据状态，以及同固件各跑次统计。`timed_with_faults` 仅是故障跑次诊断时间；只有证据核对齐全、覆盖完整且无故障停车的跑次进入清洁成绩排序。`definitely_faster_than` 只列出计时误差区间不重叠的确定提升；点估计最快并不等于软件已经最优。

## 计时工具建立时的证据（历史记录）

新增验收工具的13个测试通过：停车扣除但保留故障、未核对停车不得默认为零、出界/未完成不比较、记录缺失/哈希变化、路段重复、时间范围、误差区间、原件保护等。测试夹具是合成文本，**没有用它冒充真实跑车成绩**。

尝试被动接收 COM10，普通及提升权限的只读尝试均返回访问被拒绝；没有发送启停/调参命令，也没有强制关闭其它串口程序。本轮没有取得新的实车运行记录。工作仍需真实 C22 完整试跑、逐次故障定位及同路线行驶时间对比，才能确认四项目标是否达成。

来源层为原始源码/Markdown和 JSON（structured_parsed），时间计算与单元测试为 computed。现场覆盖与起停边界仍须用原始记录核对；没有仅凭 Markdown 或测试通过作实车完成声明。
